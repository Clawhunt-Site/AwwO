每个新增或变更功能，在动代码前至少写清下面六项；已有文档足够时只补差异，不复制出多个相互矛盾的版本：

1. **触发与结果**：用户从哪个原页面执行什么操作，最终应看到什么；同时写出加载、空结果、失败、无权限、取消状态。
2. **契约**：请求/响应样例、必要字段与单位、角色要求、错误码、超时、重试、幂等以及前端兼容策略。
3. **状态归属**：存储表/字段、租户键、事务或版本检查；哪些仅为浏览器草稿，哪些是服务器事实。
4. **实现边界**：负责模块与文件、依赖、不可同时修改的公共文件；目标能力与当前能力分别标注。
5. **验收**：成功流程、主要失败流程、越权、刷新/重连和并发场景；所需环境及实际证据入口。
6. **上线与回退**：迁移顺序、配置变更、兼容窗口、保留数据的回退方法；数据库变更不能仅靠旧镜像回退。

后续设计提案需标注「待实现/待决定」；API 表只列实际存在的路由，新路由草案另列，避免客户端误调用不存在的能力。

## 4. 前端设计与交互约束

现有 `CanvasSurface → AgentWorkspace → SessionTile / InspectorPanel`、模板、契约字段、Session 及图运行是产品依据。接口适配应集中在 SaaS API/bridge 层，减少业务协议散落到视觉组件。

- 复用既有布局、组件、样式变量、语言文案和主题机制。后端实现不自行改变节点含义、字段 ID、连线规则、会话切换或成功/失败定义。
- 用户触发动作的位置和预期结果保持一致。若需要租户选择、平台管理等新增 SaaS 入口，写明它与原账号/工作区入口的关系及兼容范围。
- 原有中英文、主题、键盘焦点与空/加载/错误反馈都属于前端验收；暂未接入时在清单中记缺口，不能通过移除入口认定完成。
- 模型、权限、任务状态和额度由服务端给出；前端不能自行宣布 ready、执行成功或获得管理员权限。错误应能让用户判断重试、恢复、重新登录或联系管理员。
- 浏览器缓存按用户、租户、画布隔离；保存须有服务器确认。CAS 冲突或网络错误保留可恢复/导出的草稿；迟到的保存响应不能清掉新的修改。
- 配置交互必须验证「界面选择 → 请求 → 服务端持久化 → Pi 实际参数 → 重载回显」。有选择器不代表选项已进入运行时。
- SaaS 节点使用“保存并准备运行”，不要求保存后再选择公司/手动绑定。宿主先确认画布保存，再调用 `initialize` 并采用返回的 canonical 文档；整图、局部运行和手动发送都经过相同准备。空 runtime/model 明示服务默认 Pi/模型，不能伪造目录或健康状态；图像选项禁用并解释当前只支持文本/编程。
- 初始化派发前同步锁定关闭和重复操作；只读、卸载、工作区切换及迟到响应都需守卫。明确拒绝保留草稿供修改，结果不确定则暂停覆盖、保留可恢复副本并重新加载核对；不能把网络异常等同于 Agent 未创建。
- SaaS 配置面板固定在画布可视区域，不随节点平移或缩放；头部关闭和底部保存始终可见，中间内容独立滚动。窄窗口运行栏换行显示，不允许操作按钮溢出屏幕或被底栏覆盖；窗口尺寸变化不得重挂载面板并丢失草稿。
- 运行提示使用当前问题的简短摘要，可展开查看并定位节点、收起或关闭。当前运行的真实 scope 进度优先于之前整图预检错误，问题变化/消失不得留下陈旧标题；完成和停止摘要也可关闭。传统入口继续本地预检，SaaS 入口由初始化后的文档统一预检。
- 只读权限需要后端拒绝写请求，前端同时提供可理解的只读状态；前端隐藏按钮不作为安全证据。

当前 SaaS 已接回原账户、邀请、语言/主题和运行设置，具体证据按 [前端对接清单](awwo-saas-frontend-contract.md)及对应日期验收记录追踪。新增团队属性面板复用原 Inspector：模型只能从目录选择，运行框架须声明 supports_node_teams 才开放配置；全量执行配置纳入持久化和结果失效指纹。reader、运行锁及错误反馈覆盖新增控件，能力声明不等于推理连通。

## 5. 后端、数据与 Pi 设计约束

**Go 是业务状态与权限的事实来源。** 一个用户可以加入多个租户；租户 owner 与平台 admin 分开。读写均验证有效登录、成员关系、角色和资源归属，不能仅靠前端传来的 tenantId 或隐藏路由隔离。

新增业务表说明主键、tenant_id、复合外键、索引、状态约束、删除策略与审计字段。保持关联对象在同一租户；本版本采用应用层过滤与数据库约束，没有启用 PostgreSQL RLS。迁移文件追加且可追踪，不编辑已部署迁移来隐藏历史。

画布 JSON 沿用前端格式；文档格式版本与 API 保存版本分别定义。关键并发写操作需明确锁或 CAS，运行去重需写明 operationId 与请求内容的关系。集合接口记录分页/上限，现有至多 200 条的列表不作为完整历史导出保证。

节点初始化以已保存 `documentVersion` 和可选 session 节点 scope 为输入，在租户授权复验、画布行锁/CAS 及当前画布活动任务检查后，原子提交 Agent、Session、初始化快照和文档。无实际文档变化不重复创建或增加版本；旧版本请求仍冲突，不能宣称 operationId 幂等回放。有效配置（包括 team）变化以新会话保留旧历史，不能覆盖已有执行证据。初始化不调用模型，验收要分别验证配置准备、实际推理及运行恢复。

**Pi 是内部执行服务。** Go 发送已经验证的任务、指令和历史；Pi 返回增量与真实终态。模型供应商、密钥、工具权限与执行环境由服务端配置。内部 token 不传给浏览器，租户不能指定任意模型 URL、宿主 cwd 或系统环境变量。

当前 Pi 为受限文本推理模式，独立子进程不等于操作系统沙箱。开放工程文件读写、shell、外部业务工具前，另写沙箱、租户文件隔离、网络权限、资源限额、交付物归属/下载及审计方案并实际验证。

运行必须包含 queued / running / completed / failed / cancelled / interrupted 语义。持久化事件先于 SSE 发布；断连不直接取消，重连不重新派发；部分文本不能判成功。仅对明确未受理的 SESSION_BUSY 作有界等待，不盲重试外部推理或工具副作用。

当前只支持单个 Go API 实例，SaaS 整图已交给 Go 按固定文档与执行快照持久调度，原本机模式仍由浏览器运行。节点团队只能使用 Pi 文本推理，tools 为空；maxTurns 计模型调用次数，不是 token 或货币预算。重启把已接受且不确定的调用标 interrupted，恢复图状态时不重新派发这些调用；未接受、依赖满足的等待节点可继续。分布式 worker、接管租约、工程文件和付费账单仍是后续能力。

## 6. 配置、秘密与环境规范

沿用 `APP_ENV=development|staging|production` 和现有 `AWWO_*` schema。端口、URL、数据库、模型、凭据、回调、队列、限额和重试等环境敏感值在首次引入时外置，不等部署时再提取。

新变量至少说明名称、类型/单位、是否秘密、必填环境、开发默认值/占位符、校验和影响的服务。对应更新 [Go 示例](../backend/.env.example)、[Pi 示例](../apps/pi-worker/.env.example)、[部署示例](../deploy/saas/.env.example)及启动文档；没有实际值时保留明确占位符。

| 环境 | 资源与验收要求 |
| --- | --- |
| development | 项目专属本地数据库、端口和测试身份；fixtures 可用但明确标注；秘密在被忽略的本地配置 |
| staging | 独立数据库、对象存储、模型凭据、OAuth/邮件/支付/回调资源；应用外层访问门、STAGING 标记、noindex、独立 cookie 和受限来源 |
| production | 真实用户资源；通过正式发布流程；上线后仅做获准的只读 smoke，不写测试用户/数据或试验性外部副作用 |

未知公网域名、模型账号、云资源和秘密不能自行借用其他项目来补齐。缺少无副作用替代方案的真实依赖时，说明所缺信息及受影响验收；继续完成不依赖该信息的代码与文档。

本文件规定的是上线验收要求，不表示当前 Compose 模板已经实现所有 staging 运维控制或已经在 Docker、公网运行。实际状态仍以验收记录为准。

## 7. Swarm 分工和串行修改点

以下为职责角色，不假定已经存在具体团队人员。每次派工由协调者记录实际 worker、基线和验收结果。

| 责任角色 | 默认写入范围 | 交付与验收 |
| --- | --- | --- |
| 前端对接 | `apps/web/src/saas/**`、必要的原组件适配、相关前端测试 | 原入口行为、协议转换、权限反馈、持久化回显与浏览器证据 |
| Go 后端 | `backend/**` | API、迁移、租户权限、状态事务及真实 PostgreSQL 验证 |
| Pi 执行 | `apps/pi-worker/**` | SDK、内部协议、进程生命周期、限额与真实 SDK 测试 |
| 协调/交付 | 根脚本、部署模板、文档总表 | 跨服务集成、版本检查、证据分级与交付说明 |

根 `package.json`、CHANGELOG、共享 API/事件字段、迁移编号和整栈测试是串行修改点：先指定一名责任人，再由其他 worker 提交需求，不并发覆盖。前后端契约变更先确定字段和兼容性，再分别实施；代码在独立 worker worktree 上保留，集成合并遵守人工批准门。

## 8. 验收与完成定义

本项目的功能完成标准是「原前端实际操作 → Go 鉴权和持久化 → 所需的 Pi 执行 → 原界面结果回显 → 刷新/重连可恢复 → 租户隔离验证」。没有模型执行的纯编辑功能只验其真实依赖，不强加推理测试。

| 证据层 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| 静态源码/顾问审查 | 设计与实现的一致性、可能的缺陷 | 命令通过、真实服务和真实账号可用 |
| 单元/组件测试 | 指定输入、权限反馈与状态转换 | 真实数据库或完整浏览器操作 |
| 本地完整进程 + 协议 fixture | Go / Pi SDK / PostgreSQL 的真实传输和持久化链路 | 实际模型服务商的认证、余额、输出质量 |
| 浏览器实际操作 | 原入口、按钮、错误反馈、保存和回显 | 未实际执行的模型调用或公网运行 |
| 真实模型账号 | 指定 provider/model 的实测调用与结果 | 所有模型、所有功能或生产准备度 |
| 镜像与 staging / production | 对应制品和环境的运行事实 | 单靠 Compose 解析、本地服务或源码测试推断的部署 |

按改动范围运行必要的测试、静态检查和构建，记录失败/跳过原因；相关检查通过后仅在新改动、失败或未解疑点出现时扩测。HTTP 200、配置 ready、任务入队或测试命令未报错不能直接替代用户功能完成。

每次交付记录：worktree、分支、来源与候选 SHA、文件/模块、原子提交、测试命令及通过/失败/跳过/阻塞、顾问结论、运行/制品/部署范围、剩余缺口。设计规范、实现、配置、变更日志和验收记录需对同一最终行为保持一致。
