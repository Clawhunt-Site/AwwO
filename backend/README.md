# Awwo Go API

Go 1.27.1, PostgreSQL, and the private Pi / OpenAI Agents workers form the SaaS backend. The API owns identity, tenant authorization, canvas persistence, sessions, messages, quotas, runs and audit events. Each worker executes only the validated request prepared for its runtime by this API.

Run from this directory with `go run ./cmd/api`. For the complete local stack use the repository's Awwo SaaS scripts. The service applies embedded SQL migrations in order on startup. It never creates an in-memory production store.

Configuration is read from `APP_ENV` and `AWWO_DATABASE_URL`, `AWWO_LISTEN_ADDR`, `AWWO_PUBLIC_ORIGIN`, `AWWO_PI_URL`, `AWWO_PI_TOKEN`, and optional `AWWO_BOOTSTRAP_ADMIN_EMAIL` / `AWWO_BOOTSTRAP_ADMIN_PASSWORD`. Development defaults bind the API to `127.0.0.1:8087`, public origin to `http://127.0.0.1:5189`, and Pi to `http://127.0.0.1:8097`. The database URL is required; sidecar tokens must have at least 32 characters when configured. Without a Pi token or ready sidecar, execution requests return 503.

Optional controls: `AWWO_SESSION_TTL=24h`, `AWWO_RUN_TIMEOUT=180s`, `AWWO_PI_SESSION_WAIT=5s`, `AWWO_AUTH_REQUESTS_PER_MINUTE=10`, and `AWWO_TRUSTED_PROXY_CIDRS` (comma-separated CIDRs, empty by default). Only requests received from an explicitly trusted proxy may use X-Forwarded-For; the chain is evaluated from right to left. Do not put arbitrary clients in the trusted proxy list. Authentication has a global four-request password-hashing concurrency limit in addition to the per-IP limit.

Public API paths begin `/api/v1`. Authentication uses an HttpOnly, SameSite=Lax session cookie; the server stores only its SHA-256 digest. Passwords use salted Argon2id (64 MiB, three iterations, two lanes). Cookies are Secure and the public origin must be HTTPS outside development. Every state-changing browser request must originate from the configured origin. Browser requests with a cross-site Fetch Metadata header are denied; JSON endpoints require application/json and reject unknown fields.

A registration creates a normal user and a tenant owner membership. The owner role does not confer platform administration. Only explicit bootstrap configuration can create an initial platform admin, and bootstrap refuses to promote an existing customer account. Bootstrap does not rotate an existing administrator password. Owners cannot be removed or demoted through the basic membership API. `PATCH /auth/profile` accepts only `{name}` (trimmed, 1–120 Unicode characters), updates the current account, and returns `{id,email,name,isPlatformAdmin}` with an audit record.

Member management supports existing registered accounts and single-use invitation links. Workspace admins and owners can list/create/revoke `/tenants/{tenantId}/invites`; only owners can create or revoke an admin invitation. Creation accepts `{role,expiresInHours?}` with role `reader|member|admin`, default 72 hours and an integer range of 1–168 hours. The response includes `{id,role,expiresAt,inviteUrl,token}`. The token is shown once, only its SHA-256 digest is stored, and listing exposes metadata without the token or hash. The browser link uses `/?invite=TOKEN`; the user must sign in, preview `GET /invites/{token}`, and explicitly accept with `POST /invites/{token}/accept`. No invitation email is sent.

Invitation preview returns `{tenantId,tenantName,role,expiresAt,status}`. Status is `active`, `expired`, `revoked`, `accepted`, `unavailable` (issuer lost permission), or `suspended`. Acceptance returns `{tenantId,role}` and preserves an existing member's actual role. Concurrent consumption is serialized by a tenant row lock; only one account can claim a token. A repeat by that same account returns its current membership without granting it again, including after the consumed invitation's expiry. A removed member cannot rejoin using a consumed token. Unconsumed expired/revoked links return 410, consumed links claimed by another account return 409, and suspended workspaces or issuers without current granting permission return 403. Acceptance, issuer membership changes, revocation and suspension share the tenant lock; key changes are audited. Revocation of a consumed token returns 409; repeated revocation of an unused token returns 204.

Tenant-owned business foreign keys are composite and queries filter by tenant ID. The durable invocation ledger instead retains a logical run ID and a tenant foreign key so deleting a completed canvas does not erase usage history. Access to foreign-tenant objects returns 404. Readers may read, members may edit/run, admins may manage ordinary memberships, and owners may appoint tenant admins. Suspension freezes tenant writes and cancels its active runs while leaving reads available. Platform administration is separate from tenant membership.

Canvas updates require the current `version` and return 409 on conflict. A rename reads the current record and submits its unchanged document with the new name and version; a conflict must not be retried automatically. Canvas deletion returns `409 resource_in_use` while any node or planner run is queued/running, and otherwise cascades its sessions, runs and events while preserving its invocation ledger. The UI requires an explicit confirmation and lists the business-data consequence. Each run has a tenant-scoped `operationId`; repeating the same operation returns the original run, while changed parameters return 409. Node runs must reference a saved canvas node and an agent in the same tenant. A session can have only one active run. Concurrent and daily UTC run quotas are checked under a tenant row lock.

Run state, text deltas and terminal events are durable PostgreSQL records. SSE supports `Last-Event-ID` and `?after=`, and revalidates the authenticated session and membership every 15 seconds. Cancellation and suspension persist terminal state before cancelling the sidecar request. If immediate follow-up execution meets Pi session cleanup, the API retries only an explicit pre-admission `409 SESSION_BUSY` for at most the configured session wait, using the same run ID and payload. Network failures, duplicate run IDs, capacity errors and already accepted streams are never retried. A restarted process marks unfinished rows interrupted and adds durable interruption events. A dedicated PostgreSQL advisory lock prevents multiple API workers for the same schema; loss of its connection causes the API to fail closed and cancel current execution. This release requires one API instance. Horizontal scaling requires durable worker leases and a shared rate limiter before lifting this constraint.

Conversation history consists of up to the most recent 100 messages in complete user/assistant pairs from completed runs. Entire oldest pairs are discarded to fit the lesser of the Pi transport budget (262144 text bytes) and the effective model context budget reported by Pi health, including current prompt, instructions and message framing. A message above 32768 UTF-16 code units excludes that pair and earlier history. Planner runs use their supplied graph/context snapshot without accumulating prior planner requests. The current prompt is never truncated. A current prompt/instructions pair exceeding the model context budget is rejected with HTTP 413 `context_limit`; Pi also enforces the same budget at its boundary. Provider availability is configuration readiness until an actual upstream call succeeds.

Canvas planning uses `/tenants/{tenantId}/canvases/{id}/plan`, accepting `{prompt,context,operationId}` and returning a standard asynchronous run. A private planner session supports empty canvases. The server validates the returned JSON operation schema and rejects execution state mutations. The frontend must still validate graph references, port types and cycles, and explicitly persist the applied proposal with canvas CAS. Planning does not modify the saved graph by itself.

Verification:

```sh
go test ./...
go vet ./...
AWWO_TEST_DATABASE_URL='<dedicated local PostgreSQL DSN>' go test -race ./... -count=1 -v
```

The database tests create and drop only their own randomly named PostgreSQL schema. Without `AWWO_TEST_DATABASE_URL`, integration tests explicitly skip. Tests exercise real PostgreSQL transactions and an in-process HTTP sidecar fixture; they do not demonstrate a real provider/model call. Runtime provider acceptance is a separate stack smoke test.

## Backend observability and usage

See [the backend observability contract](../docs/awwo-backend-observability.md) for the implemented configuration, migration matrix, permissions, nullable values, pagination consistency, pricing and persistence boundaries. This scope provides instrumentation and authorized APIs; it does not install Prometheus, Grafana, a collector, alert notifications or browser RUM.

`AWWO_METRICS_ENABLED=true` starts a separate literal-loopback listener (`127.0.0.1:9101` by default) serving `GET /metrics` and `GET /healthz`. The public API listener has no `/metrics` route. Pi and OpenAI Agents use their own loopback listeners, defaulting to 9102 and 9103. Metrics are process-local counters plus immutable 24h/30d ledger snapshots; PostgreSQL remains the source of truth for usage and estimated costs. Failed snapshot refreshes preserve the last successful snapshot and expose its age.

`AWWO_OTEL_ENABLED=true` requires a self-hosted internal `OTEL_EXPORTER_OTLP_ENDPOINT`. The exporter omits prompts, instructions, messages, output, credentials and raw business identifiers. Public trace headers are not trusted. The existing OpenAI-hosted Agents tracing remains disabled; this toggle enables the separate internal exporter. Tracing and metrics default to disabled and do not control whether the invocation ledger is written.

The four read APIs are `GET /tenants/{tenantId}/usage` (tenant admin/owner), `GET /tenants/{tenantId}/runs/{id}/invocations` (all tenant readers, with cost keys absent for reader/member), and platform-admin-only `GET /admin/observability/{summary,invocations/{id}}`. Prefix all paths with `/api/v1`. Tenant aggregates require a UTC `from`, `to` and `groupBy=day|agent|model|runtime`; usage pagination uses `pageSize=1..100` and signed cursors, separate from the older list pagination described below. Usage cursors bind a PostgreSQL visibility snapshot as well as the cutoff, expire after 24h, and become invalid after an API restart. Run pages freeze the row set, while already visible running rows may change status.

`AWWO_MODEL_PRICING_JSON` freezes operator-supplied integer micro-USD prices when reserving an invocation. Missing prices or unknown provider usage produce null estimated amounts, never guessed zero. `AWWO_USAGE_RETENTION_DAYS` defaults to 180 and validates policy input; automatic deletion is not implemented. Migrations 012–014 reconcile both historical migration-011 identities, add durable usage fields and preserve accepted runtime provenance. Partial or mismatched schemas fail startup for operator review.

The focused storage/API verification command is:

```sh
AWWO_TEST_DATABASE_URL='<dedicated local PostgreSQL DSN>' go test -race ./internal/app \
  -run 'TestUsageAPI|TestUsageCursor|TestUsageLedger|TestUsageMVCC|TestMigration|TestPricing' -count=1 -v
```

Read the verification section in the observability contract for the completed checks and the remaining integration evidence; a successful command with skipped PostgreSQL tests is not database acceptance.

The four platform administrator lists (`/admin/tenants`, `/admin/users`, `/admin/runs`, `/admin/audit`) accept `limit=1..200` (default 200) and an opaque `cursor`, returning `{items,nextCursor,snapshot}`. Follow `nextCursor` until null. The cursor fixes the first page's `createdAt` upper boundary and uses `(createdAt,id)` ordering; identical timestamps do not cause skipped or repeated records. `snapshot` is that timestamp boundary, not a consistent database backup: later commits from older transactions can become visible, deletions can remove records, and field values are read per page. Cursors are signed and bound to the requesting administrator and list. An API restart invalidates existing cursors; start the listing again on 400 `invalid_cursor`. Password/session/invitation hashes and internal request hashes are never part of these projections.

The six ordinary tenant lists (`/tenants/{tenantId}/{members,canvases,agents,sessions,runs,invites}`) now use the same response envelope, limit range and creation-time boundary. Their signed cursors also bind the actor, tenant, resource and normalized filters, with live role checks on every request. Invalid pagination returns `400 invalid_pagination`; tampered, cross-scope or restart-invalidated cursors return `400 invalid_cursor`. Canvas renames do not change creation order. Migration 005 adds membership creation times to make joining order independent of account age. Session filters `canvasId` and exact `sessionId` combine with AND. Run filters are exact `sessionId`, `operationId` and `active=true|false`; true selects queued/running records, false leaves the status unrestricted. All filters must be preserved while following a cursor. The UI requests one 50-item page at a time. A canvas history restore requests its exact session, and active-run lookup filters active records rather than searching the first 200 past runs.

Authenticated users can create additional workspaces with `POST /tenants {name}`; a successful 201 response includes the new tenant and `role: owner`. This grants no platform privileges.

Appearance is an account preference shared across the user's workspaces, stored in PostgreSQL by authenticated `user_id` (migration 006), with no caller-supplied identity. `GET /appearance` returns the original 11-preset/10-token catalog plus `{active_preset,custom,version}`. A new account starts at version 0. `PUT /appearance` accepts exactly `{active_preset,custom:{light:{token:hex},dark:{token:hex}},version}`; the version is required, a successful write increments it, and stale versions return `409 version_conflict`. Unknown presets, tokens/canvases or non-hex colors are rejected; `#RGB` normalizes to lowercase `#RRGGBB`. `GET /appearance/export` returns `{kind:"superclaw.appearance",schema_version:"0.1.0",active_preset,custom}` without identity, paths, secrets or version. The browser validates a compatible import bundle, submits only its state fields with the currently loaded version, and preserves the last confirmed state on errors. A lost write response requires reload to determine whether it committed. This API does not expose host runtime settings.

This foundation does not implement payments, email delivery, OAuth, password recovery, file uploads, tool execution, distributed workers or production rollout. Object/document retention and migration rollback policies must be decided before large-scale production use.

Node teams and durable graphs (migration 007): a saved session node may carry a version-1 `team` configuration. The API reads it from the tenant's authoritative canvas document when accepting `/runs`, snapshots it with the agent instructions/model, and never trusts a team supplied in the run POST. Each member has independent name, role, instructions, model selector, Pi runtime inheritance and `task|shared` context. Only the configured Pi model catalog is allowed; tools must be empty. Members are local configuration identities, not references to agents or sessions in another workspace.

Team bounds are 1–8 members, 1–8 rounds, 1–64 model-call admissions, and 10–1800 seconds; the first member pass must fit the call budget. The effective timeout is also capped by `AWWO_RUN_TIMEOUT`. Text limits count Unicode code points: member id/name 128, role 512, instructions 16000, model selector 256. Actual combined prompt/system bytes are additionally checked against the selected model's context limit. `sequential` runs members in order; `parallel` runs all but the last member concurrently and uses the last to aggregate; `debate` runs the configured rounds then one final synthesis call; `review` runs workers sequentially and a strict JSON reviewer each round, supplying feedback to the next pass. Review succeeds only on `{approved:true,output:string}`; exhausted rounds/budget and invalid verdicts fail. `task` excludes earlier member turns, while aggregation/review always receive their explicit operands. `shared` includes earlier completed turns within this node run. It is not a cross-tenant or cross-node memory pool.

`GET /tenants/{tenantId}/runs/{id}/turns` returns ordered persisted turns with member, role, ordinal, round, effective config, model, status, output and error. Partial member text is persisted here; only the final team output becomes the parent run's assistant message and `completed` SSE event. Model invocations use unique IDs and isolated member session keys. Each model admission consumes one tenant daily quota unit, including an uncertain/failed provider request, and concurrent invocations share the tenant concurrency cap. No automatic retry of an accepted or uncertain provider call occurs. Legacy accepted runs are migrated as one historical admission each. Restart marks unfinished turns/invocations interrupted.

`POST /tenants/{tenantId}/canvases/{canvasId}/graph-runs` accepts `{operationId,scope?,documentVersion?}` and atomically persists the original document, selected scope, resolved sessions and agent/member configuration. The server validates DAG structure, compatible ports, field types, bindings and team settings. One graph may be active per canvas. The HTTP request ends after admission; the Go scheduler independently dispatches ready nodes, runs independent branches concurrently within quotas, validates published output contracts and blocks downstream nodes when dependencies fail. Out-of-scope dependencies use non-partial cached output, explicitly labelled `cached`. Graph execution does not mutate the editable canvas document.

List graph runs with `GET .../graph-runs` (newest 50; `?operationId=...` exact lookup), inspect `GET .../graph-runs/{id}`, or cancel with `POST .../graph-runs/{id}/cancel {}`. Authorized snapshots include `id,canvasId,operationId,documentVersion,document,scope,status,nodes,createdAt,updatedAt`; each node exposes `nodeId,state,output,detail,runId,sessionId`. Readers can inspect but cannot start/cancel. The scheduler rechecks the initiating membership and tenant status before each child/model admission. On API restart waiting graph nodes resume from durable state, completed dependencies are reused, and already accepted unfinished nodes become interrupted and block their dependents. There is no paid-call replay to guess whether a lost upstream request completed. The existing single-API advisory lease remains mandatory; this is durable single-worker orchestration, not horizontal distributed execution.

For a lost graph POST response, `POST .../graph-runs/operations/{operationId}/cancel {}` serializes with admission and records a durable cancellation tombstone even when no graph exists. A delayed POST with that operation ID returns `409 operation_cancelled`. The response is `{confirmed:true,status,graphId?}`; already completed/failed graph status is preserved. Empty operation lookup alone is not proof a delayed POST cannot still arrive. Canvas deletion is denied while a graph or individual run remains active.

Cancellation reconciles the committed child status and output in the same transaction, including a completed child not yet projected by the scheduler and partial output from a cancelled child. A transient finalization error retries only database writes. Member output and invocation status commit together before the member can contribute to aggregation; parent finalization also settles remaining invocation records. Shutdown or loss of the worker lease stops persistence retries and leaves uncertain records for startup recovery. An accepted child without a local executor is interrupted, never dispatched again. PostgreSQL tests inject failures into each terminal write to verify recovery without extra model calls.

`POST /tenants/{tenantId}/canvases/{canvasId}/initialize` accepts `{documentVersion,scope?}` and returns the complete canonical canvas record, with the same fields as GET. The omitted scope selects all saved session nodes; an explicit scope must be nonempty and contain distinct session IDs. A canvas with only form nodes is a no-op. The server rechecks member-level write access, locks the canvas and compares its version. Any active node run, planner run or graph run blocks initialization with `409 resource_in_use`; a stale version returns `409 version_conflict`.

Initialization uses the saved node title as the Agent name and persona as instructions. Empty runtime/model resolve to Pi and its configured default model. Pi text and coding nodes are supported; image nodes, unsupported runtimes/models, explicit effort, unsupported tools and invalid teams are rejected. A selected session requires Pi configuration health, but initialization makes no inference requests. Agent rows, session rows, current thread identities and updated canvas bindings commit together. Compatible existing Agents/sessions are reused. Changed effective settings, including team-only changes recorded in the session setup snapshot, create a new Agent and current conversation while preserving the old Agent, session, messages and historical threads. The service never rewrites a shared Agent during initialization.

Initialization increments the canvas version only if its document changes. A compatible retry at the current version returns the unchanged canonical record and creates no duplicate Agent or session. If the response was lost, GET the canvas to recover the committed identities before retrying with its latest version; retrying the stale version is rejected. Nodes outside scope and historical threads retain their stored data. Initialization does not synchronize unrelated transcript previews on an otherwise compatible current thread.
