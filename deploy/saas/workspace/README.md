# Coding workspace sandbox

`apps/openai-agents-worker/workspace-sandbox.ts` is a trusted broker. Only the fixed Docker CLI runs on the host; generated code and shell commands execute inside the operator-built image. Build the Dockerfile with this directory as the build context and configure the worker with its immutable image digest. Runtime startup does not pull images. The image provides Node 22, Python 3 with numpy, pandas, matplotlib, openpyxl, XlsxWriter and Pillow, Git, curl, an offline headless Chromium with `awwo-check-page` (which answers three.js 0.186.1 from the image's own copy), and the `rea` code-reading CLI; it does not contain provider credentials. It supports self-contained web/game projects, Python or JavaScript tools, data scripts that write spreadsheets and charts, JSON/glTF/OBJ assets and text reports, checking a page in a real browser, and static evidence reports on a JavaScript or Electron application. Network-dependent package installs and authenticated external tools require a separate governed capability; they are not silently enabled here.

- **Chromium.** `chromium-headless-shell` is Debian's build of Chromium for automation, from the same source package and security updates as `chromium`, without GTK, D-Bus or systemd; it is also what Playwright runs for headless pages by default. `chromium-common` depends on the desktop helpers `x11-utils` and `xdg-utils`, which bring Mesa and LLVM (about 215 MB) that a headless browser never loads, so the Dockerfile first installs a local placeholder package, `awwo-headless-placeholders`, that provides those two names. Of `three`, the image keeps only the 89 files AwwO's running preview supplies (`tools/three-preview-files.json`, each with its sha256, which `scripts/preview-modules.mjs` writes with the preview's own list in `apps/web/src/canvas/previewModules.generated.ts`), its `LICENSE` and `package.json`: in the `npm ci` layer, `tools/keep-preview-files.mjs` first cuts the code three.js took from Shadertoy, Stack Overflow and OpenProcessing out of `build/three.module.js`, `build/three.core.js` and `examples/jsm/utils/GeometryUtils.js` as the web app's builds do (`tools/three-cuts.mjs`, the copy of `apps/web/scripts/three-cuts.mjs` that `scripts/preview-modules.mjs` writes), then checks the version and each file's hash, fails the build when one differs, and removes the rest, so the image holds the same three.js files as the web app ships; a worker test fails when the two lists, or the list and `tools/package.json`, part. To change a version, edit `tools/package.json` and regenerate the lockfile with the image's npm: `npm install --package-lock-only --ignore-scripts` inside `node:22.19.0-bookworm-slim`. A new `three` also needs the cuts checked against it (the release and the hashes of what they cut in `apps/web/scripts/three-cuts.mjs`, which fails the build until they match) and `node scripts/preview-modules.mjs` run again.
- **PATH.** The broker runs every command with `PATH=/usr/local/bin:/usr/bin:/bin` through a login shell (which sets `PATH` again from `/etc/profile`), so `rea` and `awwo-check-page` are symbolic links in `/usr/local/bin`; their files live, read-only, in `/opt/awwo/tools`.
- **Python packages.** A data task (a CSV summed up into a spreadsheet and a chart, an image resized) needs nothing installed: the packages above are Debian's, so they match its Python 3.11 and cost no download. On 2026-10-17 a 直接执行 task on the image without them spent 16 model calls installing pandas, openpyxl and matplotlib with pip, which do not fit the 128 MiB workspace and the 32 MiB `/tmp`, and failed. `MPLBACKEND=Agg` makes matplotlib draw to files, and `MPLCONFIGDIR=/tmp/matplotlib` keeps its font cache (built on the first import, about a second) out of the workspace and its snapshot. Debian's pip refuses to install into the system Python (PEP 668); with the web, a small extra package goes into `python3 -m venv --system-site-packages .venv`, which keeps the installed ones. The agents' instructions say all this (`WORKSPACE_SOFTWARE` in `apps/openai-agents-worker/workspace-sandbox.ts`).
- **REA** needs a procps `ps` on its `PATH` even for static JavaScript analysis, hence `procps`. `rea analyze-javascript-application /inputs/app --json > report.json` writes an evidence report whose `normalized_result.graph` holds the modules, their `imports` edges (specifier and resolved path) and Electron wiring, with the limitations of a static reading; progress lines go to stderr. It writes nothing else into the workspace. Features that need the network, a debugger attachment or native analysis engines (Ghidra, Hopper, IDA, JADX, Frida) are not available in the sandbox.

## awwo-check-page

```
awwo-check-page <page.html> [--out <dir>] [--wait-ms N] [--timeout-ms N] [--budget-ms N] [--viewport 1280x800] [--missing-ok GLOB]... [--held-clock | --no-held-clock]
```

It serves the page and the files of its directory from a private origin, `https://awwo-check.invalid/`, to headless Chromium with no network. The origin answers `GET` and `HEAD` with the files under the page's directory (symbolic links resolved, nothing outside it, 404 otherwise); because it is a real secure origin rather than `file://`, module imports, `fetch`, workers and `crypto.randomUUID` work as they do when the page is served. The three.js files AwwO's running preview supplies are the one exception, so that a three.js page meets in the check the files it would meet in that preview: a `GET` or `HEAD` for one of them at `https://cdn.jsdelivr.net/npm/three@0.186.1/<file>` (or jsDelivr's other host names `fastly.jsdelivr.net` and `gcore.jsdelivr.net`) or `https://unpkg.com/three@0.186.1/<file>` (on the default port), the addresses the preview knows (`apps/web/src/canvas/previewModules.ts`), is answered from the image's copy (`/opt/awwo/tools/node_modules/three`), with `Access-Control-Allow-Origin: *`, and listed in the report. They are the 89 files of `tools/three-preview-files.json` (`build/three.module.js`, `build/three.core.js` and 87 addons and their imports from `examples/jsm/`, the import map of a three.js page), which `scripts/preview-modules.mjs` writes with the preview's own list; a URL is read as the preview's `pinnedModuleFile` reads it (`tools/libraries.mjs`): the path as written, not decoded, and a `.min.js` naming the same file. The preview supplies only the files a page names literally (its import map and literal imports); a computed `` import(`three/addons/${name}.js`) `` gets nothing there, although the check would answer it, so a page should name its three.js files literally. Any other file of that release (`lil-gui`, the WebGPU build, the Draco and KTX2 loaders) is blocked with the reason "not one of the 89 three 0.186.1 files AwwO's preview supplies", since the preview's page could not load it either, and any other version or address (jsDelivr without `/npm/`, unpkg with it) stays blocked as any request does (2026-10-18: PALLWARD's integration tester could not run its game while three.js came only from the CDN). Every other request, `http`, `https` or WebSocket, is aborted and listed in the report (service workers are blocked, all host names are unresolvable and no proxy is used, as a second wall). It waits `--wait-ms` (default 1,500), takes a viewport screenshot, then calls `window.awwoSelfTest()` if the page defines it, for at most `--timeout-ms` (default 15,000). Chromium's profile, caches and temporary files live in a private directory under `/tmp` that is removed afterwards; nothing is written to the workspace except `--out` (default `./check-out`): `report.json` and `screenshot.png`. The check removes both first, so a run that cannot write a report never leaves an earlier one behind. A screenshot over 400,000 bytes is saved scaled down (`screenshotScale` in the report; the blank signal still uses the full one), because the output belongs to the workspace snapshot (2 MiB compressed in all); delete it when it is no longer needed. `--viewport` sides are 64–2,560. `awwo-check-page --help` prints the protocol below in short.

**Self-test protocol.** A page may define `window.awwoSelfTest` as an async function that runs the page's own tests and resolves to:

```js
{
  tests:   [{ name: string, ok: boolean, detail?: string }],        // at least one, at most 200
  planted: [{ name: string, rejected: boolean, detail?: string }],  // optional, at most 200
}
```

`planted` lists deliberately wrong variants of the code under test (an off-by-one, a missing rule) and whether the page's own tests rejected each one, which shows that the tests can fail. The result crosses over as JSON and its shape is checked: a missing field, a non-boolean `ok` or `rejected`, an empty `tests`, more than 1,000,000 characters of JSON, a throw or a timeout is reported as such and fails the check, never counts as a pass. `detail` may be omitted or `null`; names are cut at 200 characters and details at 2,000. The check cannot tell whether the tests are meaningful: that is what `planted` is for.

**Errors.** Uncaught exceptions, unhandled promise rejections (told apart through Chromium's DevTools protocol) and `console.error` messages are collected, the first 50, each at most 2,000 characters, with the phase (`load` or `selftest`) in which they happened. Chromium reports nothing for an error or rejection that the page cancels itself (`window.onerror` returning `true`, `preventDefault()`), a common way to show a friendly message, so a capture listener installed before the page's code reports those too, marked "(cancelled by the page)". While the self-test runs, console errors and errors the page cancels are listed but not counted (`listedOnlyCount`), because a self-test may exercise error paths on purpose and its own verdict covers them. "Failed to load resource" messages for the requests the check itself blocked are not counted either (they are in `blockedRequests`); a missing local file (a 404) is, unless the page fetched it as data, a picture, sound, video, a font or a text track (`fetch`, `xhr`, `image`, `media`, `font`, `texttrack`) and its path relative to the page matches a `--missing-ok` pattern: then it is listed in `missingAllowed` (with its type) and one of Chromium's own "Failed to load resource" entries for that URL is not counted (one for each excused request, so a script that misses at the same URL still counts), so a page whose large files are published beside it but cannot be in the workspace can still be checked (PALLWARD loads 45 GLB models from paths next to its page, 2026-10-18: `--missing-ok '**/*.glb'`). Missing code, a script, a stylesheet, a document or a worker, always counts, whatever the patterns, as does a file named like code (`.js`, `.mjs`, `.cjs`, `.wasm`, `.css`, `.html`) however it was asked for, and so does a message the page logs itself (a console call has arguments; Chromium's entry has none), even one that reads like that entry. The option can be given up to 20 times; in a pattern `*` and `?` match within a directory, `**` across directories and `**/` also none (so `**/*.glb` is any `.glb` file), and a leading `./` is dropped; a pattern is relative, at most 200 characters, without `.` or `..` segments, a backslash or control characters. Patterns are matched by dynamic programming (`tools/missing-ok.mjs`), never as regular expressions, which can backtrack for minutes on a long path, and a path over 2,048 characters is never excused, nor more than 2,000 distinct URLs or one over 4,096 characters. The page itself still sees the 404 and must cope with it. A renderer crash counts as an error.

**Held clock.** AwwO's render worker runs a page on a clock of its own (`apps/render-worker/virtual-time.mjs`): `setTimeout`, `setInterval` and `requestAnimationFrame` callbacks run only when it draws a frame, and it draws one only once `window.renderAt(t)` has settled, and none while it makes a page's sound. A `renderAt` or `renderAudio` that waits on the page's own timers there never finishes, though the page works in this check's first load, whose timers run (2026-10-26: the `video-program` film's kernel waited on a `setTimeout(0)` before it was ready, and its `renderAt` on the kernel; it passed this check and hung its edit). So a page that defines `window.renderAt` or `window.renderAudio` (with `--held-clock`, any page; with `--no-held-clock`, none) is loaded again, after the first load's page and the screenshot's measuring page are closed, on that same clock: once for its first frame and once for its sound, each in a fresh context, as the render worker opens a fresh page for a render and another for each sound (the frame's in `--viewport`, the sound's in the worker's 640x360 window). Each is waited on as the renderer waits on it, with the renderer's own watch (`tools/held-clock.mjs`): `window.__ready`, if the page defines it, for up to 10 s; then `window.renderAt(0)` or `window.renderAudio({ seconds: 1, sampleRate: 48000 })`, for up to 15 s. The page fails as the renderer would refuse it or miss its contract: when `renderAt(0)` or `renderAudio` waits 5 s on nothing the renderer can see but its own clock (callbacks waiting on it; no wait on real time, such as an `AbortSignal.timeout`, a delayed `scheduler.postTask` or an animation running to its end or back to its start, nor a frame whose waits it cannot read; no request, worker, Web Audio, media or frame of another origin at work; the browser's processes under a quarter of a CPU while the CPUs they may run on had half a CPU idle), with the renderer's own reason, which names what waited; when either throws there; and when it is not defined yet once the page has loaded and is ready, where the renderer looks for it, though it was in the first load. `__ready` is waited for as the renderer waits for it, until it is true and for at most 10 s, whatever the watch finds meanwhile, since a page may turn ready by work the watch cannot see. A page whose `__ready` never turns true is not failed, since the renderer renders it after its 10 s, but noted (`heldClock.note`), with the renderer's reason when the watch found it held on its clock meanwhile. A page at work is waited for, and a wait its 15 s or the budget cuts short, or one the watch could not be opened for (or DevTools would not tell it of Web Audio or media), is reported as not finished (`heldClock.unfinished`, "held clock: NOT FINISHED" in the summary): that fails nothing, but the page has not been shown to render, so the check ends with verdict `unfinished` and exit 4, and a larger `--budget-ms` may let it finish. Nothing of these loads is counted as a page error or listed as a request. The report's `heldClock` says what ran and why (`mode`: `auto`, `on` or `off`; `declares`, what the first load found; `ran`; `why`), each step (`page`: `frame` or `sound`, `step`, `ok`, `ms`, `waiting` when the page was held there, and `unfinished` when the step was cut short), the `failure` that fails the page, `unfinished`, `note` and `ms`. It costs a page ready at once a load or two (about 0.1 s for the fixtures); a page held at its `__ready` and its first frame, about 16 s; one whose `__ready` never comes and that defines both functions, about 22 s, its 10 s twice, more than the default budget leaves after most first loads: such a check ends not finished (exit 4) until `__ready` is set as the note says.

**Blank signal.** The screenshot is downscaled 4x with smoothing; the page is blank when the result has at most 2 distinct colours (4 bits per channel) and a luma standard deviation below 1, that is a flat white, black or other single-colour render. A page showing one short line of text is not blank (9 colours, deviation 2.4).

**Exit codes.** 0: the page loaded, had no counted errors, either has no self-test or every test is `ok` and every planted variant `rejected`, the render is not blank, and, where the held clock's loads ran, its first frame and its sound settled there and the renderer would find them. 1: the page failed one of those. 4: nothing failed, but a wait of the held clock's loads was cut short by its 15 s or by the budget (`verdict: "unfinished"`, `heldClock.unfinished`), so the page has not been shown to render; a larger `--budget-ms` may let it finish. 2: usage error (bad option, a value given to `--held-clock` or `--no-held-clock`, missing file, a `--wait-ms` that leaves less than 10 s of the budget). 3: the check itself could not run, for example Chromium did not start, the report could not be written, the screenshot could not be measured (when nothing else failed), the budget ran out in a step without a bound of its own, or the tool hit an unexpected error; the report, when it could be written, has `verdict: "error"`.

**report.json** (`schemaVersion: 1`): `page` and the `url` it was served at, `verdict` (`pass`, `fail`, `unfinished` or `error`), `exitCode`, `reasons`, `errorCount` (counted errors), `listedOnlyCount`, `errors` (`kind`: `uncaught`, `unhandledrejection`, `console` or `crash`; `phase`; `message`) and `errorsDropped`, `blockedRequests` (`url`, `type`, and `reason` for a library file the preview does not supply) and `blockedDropped`, `libraries` (each carried library's version), `libraryRequests` (`url`, `status`) and `libraryRequestsDropped`, `missingOk` (the patterns given, a leading `./` dropped), `missingAllowed` (`url`, `type`) and `missingAllowedDropped`, `load` (`ok`, `error`), `selfTest` (`present`, `ok`, `passed`, `failed`, `plantedTotal`, `plantedRejected`, `items` with the validated `tests` and `planted`, and `error`, `malformed`, `timedOut`, `durationMs` when they apply), `blank`, `pixels` (`distinctColours`, `lumaStdDev`, sample size), `heldClock` (above), `screenshot`, `screenshotScale`, `screenshotError`, `viewport`, `timings` (`launchMs`, `loadMs`, `waitMs`, `screenshotMs`, `selfTestMs`, `heldClockMs`, `totalMs`), `chromium` (`version`, `executable`) and `reportFile`.

**Time.** A sandbox command gets 30 seconds (120 seconds when the workspace has the web) and a command that overruns is stopped with exit 124, so the whole check ends within `--budget-ms` (default 25,000, counted from the process start), and every step also has its own bound: launch 15 s, load 10 s, screenshot 20 s, looking up `awwoSelfTest` and measuring the screenshot 10 s each, the self-test `--timeout-ms` (15 s by default rather than a longer default that could never finish inside a command), each cut to what the budget leaves after 3 s kept for closing and writing the report. The wait keeps 5 s more of the budget back for the screenshot, which seldom takes long; a heavy WebGL page on SwiftShader and one CPU can take longer (PALLWARD's world took more than 5 s on 2026-10-18), which a larger `--budget-ms` leaves room for. A page that did not load gets those 5 s for its screenshot, as before. A step the budget cut short says so in its error ("what --budget-ms had left"). A larger `--timeout-ms` is cut the same way, and the report says so; raise `--budget-ms` only where commands are allowed longer. The held clock's loads come last, with what the budget leaves after the first load (about 16 s for a page held at its `__ready` and its first frame, a second or two for one ready at once); when it leaves too little, they end not finished, exit 4. If a step without a bound of its own hangs, a watchdog writes the report, closes the browser, removes the private `/tmp` directory and exits 3 one second after the budget. A check usually takes 2–5 s. Measured under the sandbox's limits: a page that busy-loops while loading fails in 15.5 s, and a self-test that busy-loops in 19.5 s (the loop takes the container's one CPU, so the timers run late). On a host whose disk is saturated, Chromium's first launch after its files have left the page cache, or even Node's start, can take 15 s or more; the check then ends with exit 3 inside the budget.

## Sandbox limits

Every run gets a non-root container with no network, capabilities, host mounts or Docker socket, a read-only root filesystem, 1 CPU, 1 GiB memory, 128 PIDs, a 128 MiB workspace tmpfs and a 32 MiB temporary tmpfs. The workspace tmpfs allows running programs (tools a project installs, such as a bundler's native binary); `/inputs` and the temporary tmpfs are `noexec`, so programs there run through their interpreter (`node`, `python3`, `sh`). Inputs live in a separate root-owned mount and are read-only to generated programs. Container environment does not include worker/provider secrets. The host Docker service and the broker account must be restricted to trusted operators; Docker daemon access itself is privileged.

Chromium runs within these limits unchanged. Measured with the broker's exact flags while REA and every fixture page ran: at most 96 tasks (threads count against the PID limit; a WebGL page is the largest, a plain page needs about 84, so run one check at a time), 249 MiB of memory, 188 KiB and 59 inodes of `/tmp`, nothing in `/dev/shm`. The task count levels off with the CPUs the host shows (84, 91, 100 and 102 with 1, 4, 12 and 24 CPUs visible, measured before the check stopped running two renderers at once). Chromium's own sandbox needs user namespaces or a setuid helper, which the container does not grant, so it runs with `--no-sandbox`: the container is the boundary, and a page runs with exactly the rights of the generated code that wrote it.

The workspace persists across tool calls. At completion the broker produces a verified ZIP snapshot for the server to store with the tenant/session; a later run may restore only that server-authorized snapshot. Restoration rejects traversal, symlinks, special files, duplicates, encryption, excessive entry counts and size expansion. Snapshots contain regular source files, omit dependency/cache directories (`node_modules`, `.git`, `.venv`, `__pycache__`, `.pytest_cache`, `.mypy_cache`), and are limited to 2 MiB compressed, 32 MiB uncompressed and 1,024 entries. Individual published files are limited to 2 MiB. This is explicit bounded workspace continuity, not an unbounded writable host volume.

Cancellation, command timeout, helper transport failure and completion cleanup remove the whole container. Normal command exit also kills lingering untrusted child processes. A non-zero shell exit returns its exit code and captured stdout/stderr for the agent to repair and retest. Captured terminal output is bounded to 64 KiB per command. Calls on one workspace are serialized. No host shell ever interpolates a model command or file path.

The worker must call `close()` from its `finally` path. Treat a failed cleanup as a worker error and quarantine that worker from new runs until the operator resolves the Docker daemon failure. The labelled containers (`awwo.workspace-sandbox=true`) allow an operator to audit remnants after a worker or host crash; do not indiscriminately delete active containers. The daemon may be stopped or the image absent, in which case sandbox startup fails rather than falling back to host execution.

`AWWO_OPENAI_AGENTS_WORKSPACE_MAX_CALLS` defaults to 32 and accepts only 2–64. The server freezes each run's selected limit; existing 16-call runs remain bounded at 16. Every model invocation, including final delivery repair, still requires its own admission and settlement. Exceeding the frozen budget makes no extra provider request or admission, and the existing total run timeout is unchanged.

## Build and test

node --test apps/openai-agents-worker/workspace-sandbox.test.ts
AWWO_TEST_WORKSPACE_IMAGE=awwo-workspace:20261016 AWWO_TEST_DOCKER_EXECUTABLE=/usr/bin/docker \
