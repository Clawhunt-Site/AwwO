# AwwO 用户价值与付费闭环评测

2026-09-06 · 基于实际验收页面、当前源码、独立反方评审及官方产品资料

## 核心判断

**用户愿意为可以反复交付的项目付费。画布、Agent 数量和对话框本身不足以构成购买理由。**

AwwO 已具备真实 Agent 执行、独立 Session、依赖传递、范围运行和停止恢复的基础。当前用户仍需要承担配置、理解原始执行文本、找文件和判断项目状态的工作。对于已经购买 Codex 的人，这些额外操作尤其容易抵消画布带来的价值。

下一轮的核心验证是：**同一个真实需求修改两次，AwwO 能否比用户原有的 Codex 使用方式少一些人工协调、无效重跑和交付整理，同时保持质量？** 如果不能，界面更漂亮或套餐更便宜都很难带来稳定续费。

首批建议面向“每周维护客户项目、自己承担交付责任、已经使用 Codex 的技术操作者”。这是待验证的客户假设，不是已有客户画像统计。暂不同时覆盖纯非技术创业者、泛内容创作者和大型企业采购。

## 本轮看到了什么

- 实际打开 `http://127.0.0.1:15188/`，查看现有两节点画布、账号面板、交付验收节点和交付区。没有发送新 Agent 任务、创建邀请、购买套餐或改变服务器配置。
- 当前账号面板明确为单人本机可信模式，ClawHunt 账户与 AwwO 工作区分开；切换工作区只切换成员管理视图，不等于切换画布归属。
- 已完成节点的聊天仍包含完整执行提示和原始 JSON；右侧交付可读，但文件在这条路径上主要以文件路径呈现。
- 两节点画布显示“1/1 节点成功”，页面又显示可继续下游。实际有执行范围语义，用户却需要自行推断本轮完成了什么。
- 源码中的 CanvasDocument 尚无项目所有者/项目标识，使用固定 localStorage key；当前账号 API 未包含 AwwO 套餐、订单或权益接口。
- 既有真实验收主要证明规格文件、契约文本、停止与恢复等执行链。它不证明非技术用户已经能独立交付完整可发布 SaaS，也不证明多人画布隔离和商业付费已成立。

这是一轮专家走查与代码审查，未做外部用户访谈、付款实验或统计性可用性测试。下文所有人数、价格和指标均为建议的试验设计。

## 用用户的五个问题重新组织产品

| 用户的问题 | 当前障碍 | 应当做出的产品变化 | 形成的购买理由 |
| --- | --- | --- | --- |
| 这能帮我完成什么？ | 首屏突出画布与 Agent，结果范围不够具体 | 展示一个可验证场景，例如“给现有后台补会员权限，交付变更与验收结果”；保留通用输入，但不承诺任意任务自动完成 | 与当前工作有关，值得尝试 |
| 为什么还要我配置这么多？ | 生成画布后逐节点绑定、选环境、补字段 | 复用已确认的 Codex 环境，集中准备一次；只问阻止执行的缺失信息 | 比自己编排多个会话省事 |
| 做完了吗？结果在哪里？ | 聊天、JSON、路径、状态分散 | 每次结束给出完成内容、尚未完成、可打开成果、证据和下一步；有实际引用才提供预览/下载 | 结果可检查、可采用、可交付 |
| 客户改需求之后怎么办？ | 已有范围执行，影响和旧成果来源不直观 | 预览本次影响，保留无关成果；选择当前节点或受影响部分重新执行；显示使用的输入与成果版本 | 修改时省协调、省返工，是区别于单次聊天的关键 |
| 下周回来还在吗？付费包含什么？ | 图主要留在浏览器，身份与服务边界分散 | 项目可靠保存/恢复、成果归属清晰、账单和模型费用分开；到期可以读取和导出历史成果 | 可以放心投入长期工作 |

默认界面延续上一份轻量方案：总览看分工；进入节点时只突出当前对话；Session 与交付物按需展开；契约、模型参数和原始事件进入详情。保留用户手动调整结构的能力。

## 应优先跑通的一个场景

选择用户自己的一个已有项目，例如为后台增加两种角色的访问控制：

1. **说明目标与范围**：选真实代码目录，输入需求和完成标准，确认现有 Codex 环境。
2. **得到最少必要分工**：起始可以用需求、实现、验收三个节点；简单任务允许更少，不强制每个项目三节点或七模板。
3. **完成首次交付**：用户打开实际变更/文件和验证结果。验收区区分“Agent 自述”“文件已读回”“测试确实运行”，不能把一段 Passed 文本当成功能测试。
4. **提出一次有意义的修改**：例如普通会员不得查看其他用户资料。先看影响，再更新必要部分，已确认的无关成果保留。
5. **重新交付并回来继续**：关闭后重新打开，找到项目、会话、版本和成果；能继续处理第二次要求。

完成第 4–5 步，用户才真正体验到 AwwO 的额外价值。试用应覆盖“首次交付 + 至少一次修改与重新交付”，不能在第一次结果之后立刻挡住这个循环。

## 付费心理如何自然形成

付费应建立在以下事实的连续发生上：

**我的任务适用 → 我能自己开始 → 我拿到了可用成果 → 第二次修改更省事 → 我愿意把下一项工作放进来 → 购买持续使用。**

- 价值感：呈现本次实际交付和省掉的操作。可显示“本次只更新 2 个节点，复用 3 份已确认输入”；不要无依据声称节省数小时或成本降低百分之多少。
- 控制感：运行前说明作用范围和资源来源；可停止，可恢复，未确认终态先核对；超出明确预算上限前暂停新派发。
- 资产感：需求、会话、规则和交付可持续找回，用户能复制流程用于下一项目。基础可靠性和取回自己的成果不是高价套餐专属。
- 信任感：收费对象、价格、续费、取消和模型消耗清楚。无真实成功证据时明确显示未完成，产品故障不通过重复派发让用户承担不明费用。
- 升级时机：完成一轮真实交付及修改后，用户主动开启下一项目、需要持续保存或实际托管能力时，展示与需求对应的服务。费用信息从试用开始就可查看，不到最后才披露。

NN/g 建议界面突出当前任务的主要动作、避免过早索要承诺，并用真实用户检验第一印象；这些原则支持上述顺序，但不构成 AwwO 转化率的证据。[官方文章](https://www.nngroup.com/articles/first-impressions-human-automaticity/)

## 收费对象与初始包装

### 首批：个人版软件服务，自带 Codex

用户购买 AwwO 持续使用、项目组织、成果管理与明确范围的支持服务。具体只能列入已上线并验收的能力。

**AwwO 订阅与用户自己的 Codex 订阅/额度分开。购买 AwwO 不增加 Codex 额度、不解锁模型、不保证无限运行。** Codex 额度耗尽时准确指向其资源来源，不能把购买 AwwO 当作恢复额度的解决方法。

| 阶段 | 可交付的服务范围 | 费用设计 |
| --- | --- | --- |
| 受邀试用 | 有期限和明确范围；完成一个真实小项目、一次有效修改及成果取用；模型使用用户自己的环境 | AwwO 软件服务免费试用，模型费用另行说明；不要求为了取走成果付款 |
| 个人版付费试点 | 单操作者、已验证的项目和交付能力、明确支持范围；不宣称多人协作或托管 | 可以先探索 ¥99/月与 ¥199/月两个明确报价假设；金额未确定，也未上线 |
| 后续托管或团队方案 | 只有在真实提供隔离运行、托管资源、共享权限、团队交接后再开放 | 软件服务、实际托管资源和模型资源分别计价；团队费用必须对应真实协作能力 |

两种价格不能仅凭 10 人试点判断高低优劣。先收集真实拒付原因、任务频率、替代工具和人工支持时间，再确定适合的报价。各组服务与支持范围要一致；不能将大量人工陪跑成交算作自助软件转化。

不建议按节点数或消息数定价：节点拆分是产品鼓励的控制方式，消息多也不等于价值大。并发额度若影响实际托管成本，可以作为资源限制，但必须在能力真实存在之后说明。

试用或订阅到期后保留历史读取、导出和安全的停止/恢复；收费限制作用于明确的新服务。不把停止按钮、旧文件或失败恢复作为迫使续费的手段。

### 竞品参照的正确用法

Lovable 的官方定价说明将工作区共享资源、构建和运行消耗放进套餐解释；Replit 的官方页同时提供免费体验和付费容量、并行、协作、恢复等差异。这说明用户会比较可完成的工作、容量和持续服务。**不能据此推断 AwwO 已拥有这些能力或用户必然接受相同价格。** [Lovable 定价](https://lovable.dev/pricing) · [Replit 定价](https://replit.com/pricing)（2026-09-06 查阅，具体套餐会变化）

## 真正的收费闭环需要补什么

当前旧设置页存在 ClawHunt 套餐和中转余额，底层存在成本/预算接口；它们尚未与 Codex 画布组成 AwwO 的购买权益链。先明确唯一的服务购买主体与权益归属，复用已验证能力时保持契约边界。

自助收费至少需要：

1. 服务端维护版本化价格与权益，明确用户/项目归属。套餐卡只是展示。
2. 创建可追溯订单和结账会话；展示币种、计费周期、服务范围、模型费用和续费方式。
3. 由可信的服务端支付确认更新订单；不能凭前端“支付成功”跳转发放权益。
4. 订单事件幂等，发放和失效可重放核对；支付成功但权益未到账有明确恢复路径。
5. 续费失败、取消到期、退款等同步到权益；取消订阅与立即失效是不同状态。
6. 运行派发在服务端检查授权、有效权益和资源上限；不依赖前端隐藏按钮，续费事件也不自动重跑旧任务。
7. 用户可以看到套餐、账单、续费状态、资源归属、取消入口和历史成果。
8. 在独立沙箱验证购买成功/失败、重复通知、权益恢复、取消/退款、额度上限、会话恢复和跨用户隔离；本轮没有进行任何真实购买。

早期若提供收费部署或陪跑，应明确是“部署与支持服务”，列清实际交付和人工投入，不包装成已经完成的全自动 SaaS。

定价前按真实试点核算：每付费用户服务收入减去支付费用、实际托管、存储及支持投入。自带 Codex 时其模型账单归用户原有供应关系；后续提供托管模型时才把相应实际成本纳入。没有成本样本前不承诺“无限量”。

## 如何验证，而不是只问用户愿不愿付钱

### 第一轮：5 位目标用户的可用性测试

采用用户真实已有任务，观察其是否能独立连接环境、完成交付、修改一次要求并重新取用成果。记录求助次数、卡点、人工整理时间和产物是否真实可用。与原有 Codex 使用方式比较时尽量用难度相近任务，并记录任务差异；小样本用于发现问题，不作统计推广。

### 第二轮：10 位同一细分人群的付费试点

明确告知价格和服务范围后，观察实际订单、使用和续费。提供真实价值验证阶段，不以访谈者礼貌回答“愿意买”判断通过。暂不自动发送招募、报价或扣款。

| 指标 | 严格定义 | 用途 |
| --- | --- | --- |
| 首次价值达成 | 用户打开并采用至少一份有实际引用、可验证的交付；生成图和发送消息不计入 | 验证用户是否拿到结果 |
| 修改循环完成 | 首次交付后完成有意义的修改、重新验证和取用，并保留不需更新的成果 | 验证 AwwO 相对直接聊天的价值 |
| 7 天复用 | 用户因真实新要求主动返回继续，不把客服催促下的演示算入 | 判断持续使用动机 |
| 激活后付费 | 已完成修改循环且收到明确报价的用户中，实际完成服务购买的比例 | 区分产品价值与付款障碍 |
| 续费 | 第一周期实际使用后再次付款，并记录退款与取消理由 | 判断订阅是否成立 |
| 服务成本 | 每位用户的支持分钟数、托管/存储实际成本、失败重试与恢复成本 | 判断成交是否可持续 |

埋点应使用真实 account/project/session/run/artifact/order 标识关联，采集必要事件而非默认收集私密提示词和源码。付款、权益、运行、产物各有独立事实源，不能把一个前端按钮点击当作全链路完成。

如果用户没有完成第一次价值循环，优先修产品；如果用得少，检查任务频率和重复价值；如果长期使用却拒付，检查替代品与服务范围；如果成交依赖重度支持，评估服务型产品而非强行解释为自助 SaaS 成功。

## 实施顺序与验收门

| 顺序 | 必须交付 | 验收方式 |
| --- | --- | --- |
| 1. 让任务读得懂、开始得了 | 自然语言对话投影、已接受草稿消费、作用范围明确、环境集中准备 | 新用户完成真实小任务；刷新、停止、恢复不丢输入或重复派发 |
| 2. 让项目和成果留得住、拿得走 | 项目身份与可靠保存、受控产物引用、预览/导出、真实成果归属 | 关闭重开、跨授权边界、文件取用和失效路径实测 |
| 3. 证明第二次修改有优势 | 变更影响预览、按范围执行、复用来源与版本、成果重新验证 | 与现有方式对照，确认无关执行减少而质量未降低 |
| 4. 小范围真实付费 | 明确个人版范围与报价、订单和服务交付、支持成本记录 | 真实成交和复用；数字仅报实测，不预设转化结论 |
| 5. 自助订阅 | 服务端订单/支付/权益/失效闭环，账单与退出路径 | 独立支付沙箱及端到端权限验收 |

前三项达到可独立使用之前，不建议扩大投放或同时推出多个团队套餐。若目前只能靠陪跑达成交付，可以先验证有限范围服务收入，明确其人工属性。
